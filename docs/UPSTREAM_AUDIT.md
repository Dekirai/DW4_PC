# Digimon World 4 native-port source audit

Audited 2026-09-07. Reference checkout: `ivanno4317/dw4-gc`, commit `794294e17fef0b3ab5eeb15fda9bd57b0dc98a2b` (2026-08-08). No `AGENTS.md` was present in this checkout or the applicable workspace ancestors.

## Finding

The reference is a GameCube matching-decompilation project, not an existing native port or a complete gameplay source tree. Its build uses Metrowerks Gekko/PowerPC settings and links a DOL. Reconstructed console SDK and standard-library objects account for almost all checked-in source. It is useful for addresses, compatibility behavior and reverse-engineering evidence; it cannot currently supply a working native gameplay runtime.

This is split coverage, not verified reconstructed-code coverage.

## What the engine files actually implement

`Alchemy/src/igGap.cpp` defines an ArkCore pointer accessor and initialization/release wrappers; `Alchemy/src/igCore/igArkCore.cpp` defines a version check. The three non-inline functions have known DOL locations:

| Function | Address | Symbol size |
| --- | --- | ---: |
| `Gap::igRefAlchemy(int)` | `0x8003CFC0` | 172 bytes |
| `Gap::igReleaseAlchemy()` | `0x8003D06C` | 244 bytes |
| `igArkCore::checkAlchemyVersion(int)` | `0x8003D1C8` | 108 bytes |

These 524 bytes of assigned engine text are both marked NonMatching. Required implementations such as `igArkCore` construction, allocation, bootstrap, core startup/shutdown, and class registration are absent. Several headers are skeletal; `igFile` has no file operations. No gameplay source for actors, maps, combat, inventory, saves or the game loop exists in this tree.

## Concrete reusable references

- `dolsdk2004/pad/Padclamp.c`: signed-stick dead zones, octagonal/circular clamps and trigger range handling. `PADClamp` is identified at `0x802624CC`. These can support an original-input compatibility mode after independent native adaptation and verification. The presence of `PADClampCircle` in SDK source alone does not establish its use by DW4.
- `dolsdk2004/mtx/mtx.c`: scalar `C_MTX*` implementations provide transformation equations. Its `PSMTX*` routines use PowerPC paired-single assembly; neither the entire file nor the GPU SDK can simply be compiled for x64. The DW4 symbols identify a subset of `PSMTX*` routines.
- `Runtime/MSL/Common/rand.c`: a 32-bit LCG (`1103515245`, `12345`, upper 15 output bits) offers a tiny behavior fixture. This does not prove DW4 gameplay uses it as its main RNG.
- Symbol addresses, object splits and expected DOL checksum are directly useful for naming and validating reconstructed functions.
- zlib 1.1.3 and libpng 1.0.8 document the linked formats. Their presence does not supply the missing AFS or Alchemy IGB asset loaders.

## Verified local input and provenance

The user's extracted `sys/main.dol` is 5,196,512 bytes with SHA-1 `e409a88a7379ed1a536f93b0a303a0ce7cd5d877`, exactly matching the reference `config/GDJEB2/build.sha1`. The repository README labels its supported input `GDJEB2`, USA Rev 1; the user's actual `boot.bin` revision byte is 0. Preserve this distinction: the exact DOL hash matches, despite the differing revision label. The local asset directory contains `area.afs` (511,553,536 bytes), `ndmw.afs` (692,326,400), `ndmw.igb` (107,527), and `opening.bnr` (6,496).

The root repository notice is CC0-1.0. Embedded notices in `src/zlib/zlib.h` and `src/libpng/png.h` retain their respective third-party copyright/license terms. Root CC0 alone is not evidence of uniform third-party provenance: selected SDK/MSL/Alchemy files have no individual provenance statements. The README says game data must be supplied by the user. Preserve source attribution and applicable notices; keep the ISO, DOL, extracted assets, generated disassembly and asset-derived fixtures out of the public source repository. This is a record of the observed notices, not a separate legal clearance assessment.

## Recommended next native target

Build a bounds-checked AFS reader and Alchemy IGB v6 metadata reader, then decode one original texture/mesh into a native asset viewer. The format metadata exposes object classes and field layouts, which can guide actual engine reconstruction. A successful native settings window alone should not be counted as playable-port progress.

Separate host display/input/audio/filesystem services from original fixed-step simulation, asset readers and the renderer. Use explicit integer widths and byte order for disk data; never reinterpret original PowerPC pointers as host pointers. Keep modern display rate independent of simulation rate until timing assumptions are measured. Later online co-op requires identified serializable authoritative state and RNG/timing behavior; texture replacement requires stable asset IDs; custom gameplay requires working object loading first.

Acceptance for the immediate target: native tests reject malformed archive/IGB offsets and counts; the user's files are read without alteration; the viewer identifies or renders verified original content; documentation states exactly which data and engine stages remain unimplemented.
